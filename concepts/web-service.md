# Концепт: Веб-сервис

Где живет (опционально):
- Распределённые вычисления / Сервис-ориентированная архитектура (SOA) / Облачные технологии

Что это:
- Способ взаимодействия двух приложений по сети, при котором одно приложение предоставляет функциональность, а другое её запрашивает.
- Взаимодействие строится на контракте (интерфейсе), описывающем доступные операции и форматы данных и скрывающем детали реализации.

Синонимы:
- Web-сервис
- Веб-API
- HTTP-сервис

Не путать с:
- API
  - Почему можно спутать: Оба термина описывают интерфейс для взаимодействия программ. Веб-сервис часто называют API.
  - Почему различаем: API — любое программное взаимодействие (библиотека, ОС, драйвер). Веб-сервис — это API, доступное по сети через стандартные веб-протоколы. Не всякий API является веб-сервисом, но всякий веб-сервис является API.

- Микросервис
  - Почему можно спутать: Микросервисы часто реализуются как веб-сервисы и общаются по HTTP.
  - Почему различаем: Микросервис — это архитектурный стиль организации всей системы (независимые, мелкие, развёртываемые отдельно). Веб-сервис — это способ связи между компонентами, который может использоваться и в монолите, и между микросервисами.

- Сайт / Веб-приложение
  - Почему можно спутать: Оба доступны через браузер и используют HTTP.
  - Почему различаем: Сайт/веб-приложение ориентированы на человека (интерфейс, HTML). Веб-сервис ориентирован на другое приложение (данные в JSON/XML, без визуального интерфейса).

Вложенные концепты:
- Контракт (интерфейс)
- Операция (вызываемое действие)
- Конечная точка (endpoint)
- Сообщение: запрос и ответ

Категории:
- По синхронности
  - Что это: меняет поведение клиента — блокирует ли он выполнение до получения ответа.
  - Пример: синхронный (запрос-ответ) и асинхронный (webhook, очередь сообщений).
- По способу взаимодействия
  - Что это: меняет то, как клиент обращается к сервису — вызывает операции, работает с ресурсами или описывает запрос.
  - Пример: вызов операций (RPC), работа с ресурсами (REST), декларативный запрос (GraphQL).

Примеры:
- Пример: Платёжный шлюз (например, Stripe API), который принимает HTTP-запрос с данными карты и возвращает JSON-ответ об успехе или ошибке.
- Пример: Сервис погоды, предоставляющий по GET-запросу /weather?city=Moscow текущую температуру в формате JSON.
- Антипример: Локальная библиотека для работы с датами (datetime в Python) — это API, но не веб-сервис, так как работает внутри процесса без сети.
- Антипример: Статический HTML-сайт — использует HTTP, но не предоставляет программный интерфейс для вызова операций другим приложением.

Рамки (границы модели ценности):
- Веб-сервис без потребителя
  - out_of_scope: Сам по себе факт наличия веб-сервиса; ценность рассматриваем только в связке со сценарием потребления.
  - why: Без сценария, где автоматизация обмена данными экономит время или деньги либо открывает новые возможности, ценность не возникает.

- Веб-сервис, дублирующий существующий или незрелый
  - out_of_scope: Веб-сервисы, которые дублируют существующий аналог, не имеют документации, не поддерживают версионность или требуют уникального формата.
  - why: Затраты на интеграцию могут превысить выгоду.

- Веб-сервис, раскрывающий детали реализации
  - out_of_scope: Сервисы, жёстко привязанные к внутренней базе данных или требующие знания деталей реализации.
  - why: Это не сервис, а «удалённый вызов процедуры»: накладные расходы на сеть без преимуществ изоляции и независимого развёртывания.
